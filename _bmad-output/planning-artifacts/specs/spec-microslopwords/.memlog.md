- (note) Why: users need local-first cross-platform DOCX editing without heavy suites or account-bound web tools, preserving common documents with deterministic layout and a small hackable codebase.
- (constraint) Stack is locked to .NET 10 net10.0, Avalonia 12.1.4, SkiaSharp 3.119.4, HarfBuzzSharp 8.3.1.3, and Open XML SDK 3.5.1; Avalonia, Skia, and HarfBuzz move only as one reviewed set, with centralized package versions.
- (constraint) One-way dependencies: Core has no UI, OOXML, Skia, or filesystem concern; Layout is a pure deterministic function; Rendering consumes layout and never reflows or mutates; OOXML lives only in Formats.Docx; new dependency edges need an ADR.
- (constraint) Model and edit integrity: immutable records; section, block, and run IDs are stable for one document lifetime and never reused; every edit is an invertible command through one history; a new edit clears redo; one writer mutates state and stale async results are discarded.
- (constraint) Local-first and untrusted input: no macros, ActiveX, OLE, scripts, or embedded executables; no network fetch during open, edit, save, print, or PDF; enforce package and image limits plus traversal and zip-bomb rejection; use atomic temp-write saves; no telemetry or content and path logging.
- (constraint) Screen, print, and PDF consume one deterministic layout; with the same document state, styles, page settings, fonts, and engine versions, repeated runs produce identical geometry and pagination on a platform.
- (constraint) Release self-contained desktop builds for Windows x64/arm64, macOS Intel and Apple Silicon, and Linux x64 with no admin rights or separate .NET, using native file and print dialogs and platform modifiers.
- (constraint) Keep the codebase small; warnings are errors; use xUnit v3 and Shouldly; require layout goldens, a release DOCX corpus of at least 30 documents, architecture tests, and build/test/format gates on Windows, macOS, and Linux.
- (constraint) Performance on 2020-or-newer 4-core, 8 GB RAM, SSD reference hardware: 50-page 20-image document opens in 3 s or less, keystroke paint is 50 ms p95 or less, scroll and zoom are 100 ms p95 or less, 10 MB save is 2 s or less, PDF export is 5 s or less, and peak memory is 500 MB or less.
- (constraint) The v1 UI is English-only and has no cloud, account, collaboration, plugin marketplace, or telemetry dependency.
- (capability) CAP-1 document lifecycle: create, open, save, save-as, dirty state, atomic writes, and local recovery snapshots; success covers non-destructive failures, source-safe recovery, and reopen fidelity.
- (capability) CAP-2 text editing: Unicode typing, IME composition, paragraph split and merge, soft line breaks, and grapheme-aware deletion; success requires exact-once IME commit, one-paragraph minimum, and reversible structure edits.
- (capability) CAP-3 selection and caret: pointer and keyboard placement, range selection, and navigation at every supported zoom; success requires grapheme hit-testing, anchor extension, multi-page selection, and stable viewport tracking.
- (capability) CAP-4 clipboard and history: cut, copy, paste, undo, and redo; success requires rich internal paste, basic plain-text and HTML interop, coalesced typing, one-step replace-selection, redo clearing, and exact restoration.
- (capability) CAP-5 character, paragraph, list, and named-style formatting; success covers direct formatting and clearing, nine list levels, built-in and user styles, live style edits, and DOCX style round-trip.
- (capability) CAP-6 find and replace: case-sensitive and whole-word search across runs with counts, wraparound, formatting inheritance, and one-step replace-all; success includes no-match caret stability and no replacement loops.
- (capability) CAP-7 tables: create and restructure tables, edit cell content, merge and split cells, set widths, borders, shading, and header repetition; success requires intact rows, editable imported tables, and round-trip through print and PDF.
- (capability) CAP-8 inline images: insert, size, describe, and remove embedded PNG/JPEG/GIF images; success covers aspect preservation, alt text, undo, safe rejection, placeholders for corrupt media, and round-trip.
- (capability) CAP-9 headers, footers, and page numbers: per-section editing, first-page variants, link and unlink, and live current/total page fields; success requires formats, restart values, repagination updates, and print/PDF agreement.
- (capability) CAP-10 deterministic pagination, rendering, and zoom; success requires stable geometry, no supported-content clipping, immediate repagination, 25-400 percent zoom, fit modes, pointer anchoring, and accurate caret and selection overlays.
- (capability) CAP-11 print and PDF export from the same layout; success requires page ranges, preview agreement, searchable text, embedded or subset fonts, complete headers and footers, and no partial output on failure.
- (capability) CAP-12 DOCX import, export, round-trip, unsupported-content handling, and security; success requires 100 percent text and at least 95 percent supported-construct survival, opaque preservation, default-cancel loss warnings, corpus reopen without repair, and rejection or non-execution of active or external content.
- (capability) CAP-13 accessible cross-platform shell, settings, and theme; success requires keyboard-only core journeys, screen-reader state, high contrast and 100-200 percent scaling, persistent light/dark/system settings, and self-contained launch on clean systems.
- (capability) CAP-14 headless CLI for inspect, validate, to-text, and export-pdf; success requires deterministic JSON, data on stdout and diagnostics on stderr, stable documented exit classes, read-only behavior except explicit output, and desktop-equivalent PDF pagination.
- (decision) Success signal is a 30-or-more document release corpus with 100 percent text and at least 95 percent supported-construct survival, clean reopen in Word and LibreOffice, and green build, test, and format gates on all three platforms.
